# Recording dependency verdicts durably

## Label + comment, both head-bound

- **Labels** are the index: scannable, filterable, survive the session. Use a dedicated prefix (for
  example `dep:merge`, `dep:verify`, `dep:investigate`, `dep:hold`, `dep:close`) so they sort together
  and never collide with ecosystem or domain labels. Create them idempotently (`gh label create …
  --force`).
- **Exactly one verdict label per PR at any time.** A PR carrying two is worse than unlabeled,
  because the list view now lies. Remove all verdict labels and add the new one in one edit
  (removing a label the PR lacks is a no-op).
- Apply labels after the first adjudication (including interim ones, so an interrupted run is
  recoverable) and again after re-adjudication. At the end, query for remaining interim labels; a
  non-empty result means a phase was skipped.
- Do not strip the verdict label when the PR merges or closes; it is the audit trail.
- **Comments** are the record. Template:

  ```markdown
  ## Dependency review

  **Verdict:** <Merge / Hold / Close>
  **Head:** `<full reviewed SHA>`

  <one-line reason>

  ### Investigation
  <Investigate PRs only: question, answer, citations.>

  <details><summary>Full review</summary>
  <full review>
  </details>

  <!-- <machine-readable marker> -->
  ```

- No signature or "generated by" line. Post from a body file. If one post fails, report it and keep
  going.

## Idempotency of the record

A raw marker grep is not an idempotency check: an existing record can name a stale head or the
opposite verdict. Reuse a record only when exactly one marker matches the current full head and
verdict. Otherwise, in order: edit your own existing marker in place; if a contradictory marker by
another author must go and permissions allow, record its author, URL, time and verdict durably
before deleting (deletion is irreversible); if deletion is denied, post one current marker that
links and supersedes the stale one. Never leave two apparently-current verdicts.

A verdict record is a *current-state* report: wording like "manifest-only" or "no lockfile" goes
stale after a lock commit and must be edited, even though it was true when written.

To correct a posted record, rewrite the whole live body, not one line: fetch it, edit, write it
back, fetch it again. Then search the result for each old wording (zero hits), diff it against what
you sent, and confirm the verdict and head markers survived. A stale sentence left anywhere costs a
review round.

## Check evidence: two clauses, always

Name the local commands that passed, then state the live provider rollup separately. Never write an
unqualified "checks pass" while any provider check is failed, queued or awaiting approval. A failure
reproduced on the base is non-blocking, not passing. If checkout or setup failed before project
commands ran, say that project CI did not run.

When a provider job failed: read the job metadata and its steps first (it proves whether project
commands ran), group failures by failed-step signature, and download one representative log per
signature into a scratch dir with a failure-preserving block (`set -euo pipefail`, write to a temp
file, `test -s`, then move). Search for exact runner markers (`##[error]`) and their neighbours,
never broad words like "failed", which persistent-runner cleanup floods. Checkout failing to clean a
persistent workspace is a runner gate only if the same class is on the base tip.

## Counts keep their unit

Reproduce every numeric inventory with a dedicated count query. Occurrences, files and jobs are
different claims; never infer a total from context-expanded search output. Timestamp rollup counts
while any check is still running, or name the completed jobs instead.

## Reviewing another steward's verdict record

Grade two things separately: the dependency verdict, and the completeness of the executor's record.
A correct Hold still needs one matching label, one current marker, and an adverse review at the
pinned head. If the dependency is clearly safe but the record is stale, preserve the verdict
(comment-only review stating the artifact verdict and the exact report fixes) and request changes on
the *tracker task*, not the PR. Never block a safe dependency PR to express a defect in the report.
After a provider write, read back head, review state, labels, markers and checks before deciding
the tracker stage.
